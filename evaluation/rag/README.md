# Поиск Артёма: состояние и подключение

Реализован локальный BM25, а не гибридный поиск. Новых зависимостей нет:
`kb_loader.py`, `chunking.py`, `retrieval.py` используют стандартную библиотеку
Python и общие типы `contracts.py`. Контракт версии 1 не менялся.

## План и готовность

1. **Готово:** загрузка всех Markdown из ZIP/каталога, проверка путей, UTF-8 и размеров.
2. **Готово:** нарезка по заголовкам с сохранением таблиц, полных абзацев и хвостов.
3. **Готово:** BM25, нормализация русских окончаний, ё, чисел, единиц и короткий
   словарь бытовых синонимов; стабильные ID, источники и кэш фрагментов.
4. **Готово:** технические тесты, ручная разметка локального набора,
   сравнение двух лексических вариантов, измерения и разбор пропусков.
5. **Следующий этап:** BAAI/bge-m3 и гибрид на том же наборе. Нужны адрес прокси,
   доступ и подтверждённая схема embeddings API. Локального `.env` пока нет.
   Для независимого сравнения потребуется дополнительный набор, не использованный
   при разработке. Реранкер подключать только после измерений.
6. **После подключения Платоном:** проверить ответы общей LLM и сквозной сценарий.
   Отправкой конкурсного сабмита распоряжается Платон.

## Подключение Платоном

Из корня проекта:

```python
from pathlib import Path
from retrieval import build_retriever

retriever = build_retriever(
    Path("data/knowledge-base.zip"),
    cache_dir=Path("runtime/index"),
)
chunks = retriever.retrieve("Какие данные нужны для оценки системы учёта?", top_k=6)
for chunk in chunks:
    print(chunk.source, chunk.title, chunk.score)
```

Создать объект один раз при запуске, затем переиспользовать. `retrieve` синхронный,
не меняет индекс или историю клиента, допускает параллельные вызовы из потоков.
В асинхронном API выполнять синхронную работу вне event loop. Историю и уточнение
запроса делает ядро консультации, не retriever.

Результат — `list[KnowledgeChunk]`: `chunk_id`, относительный `source`,
`title`, `text`, `score`. Не более `top_k` уникальных ID, по убыванию score.
Пустой запрос, стоп-слова и отсутствие лексических совпадений возвращают `[]`.
`top_k` должен быть целым положительным числом (не `bool`). Нет базы —
`FileNotFoundError`; некорректная база — `KnowledgeBaseError`/ошибка чтения.
Ошибки не превращаются в выдуманные результаты.

BM25: положительный Robertson IDF, `k1=1.5`, `b=0.75`.
Нормализация окончаний упрощённая, без полноценной лемматизации и исправления
опечаток. Это ограничение первой версии, а не эквивалент смыслового поиска.

## Вход, нарезка и кэш

- Принимается ZIP или каталог с `.md` без учёта регистра; вложенные файлы читаются
  полностью. BOM и CRLF нормализуются. ZIP никогда не распаковывается на диск.
- Запрещены переходы `..`, абсолютные/Windows-пути и символические ссылки.
  Дубли нормализованных путей — ошибка. Не-Markdown файлы не индексируются.
- Пределы: ZIP 128 МиБ, документ 8 МиБ, суммарный текст 64 МиБ, 10 000 entries.
  Пустые, бинарные и не-UTF-8 Markdown считаются ошибкой.
- Заголовки ATX (`#`–`######`) сохраняются в иерархии. Заголовки в fenced code
  не делят текст. Раздел до 5000 символов тела сохраняется целиком; в большем
  обычном тексте возможен разрыв между абзацами с перекрытием последнего абзаца
  до 500 символов. Структурированный раздел с таблицей/списком не дробится:
  предел мягкий. Даже очень длинный абзац не обрезается.
- Соседние разделы не всегда попадают в один фрагмент. Наличие оговорки в базе
  не гарантирует её попадания в выдачу. Ядро должно проверять достаточность
  найденных доказательств. Нельзя отрезать конец фрагмента ради лимита контекста.
- ID зависят от относительного пути, содержимого и версии правил. Перестановка
  файлов в ZIP не меняет выдаваемые ID; ZIP и каталог эквивалентны.
- JSON-кэш хранит **фрагменты**, а не готовые postings BM25. Ключ включает хеши
  документов, правила нарезки и нормализации. База перечитывается для проверки
  актуальности, postings строятся при создании объекта. Кэш не нужен для работы
  и не даёт существенного выигрыша на этой маленькой базе.
- Запись кэша атомарна. Повреждение вызывает предупреждение и перестроение;
  недоступный каталог — предупреждение и работу в памяти. Старые версии файлов
  кэша не используются, но автоматически не удаляются.

Кэш содержит закрытый текст. Хранить только в игнорируемом `runtime/`;
никакие исходные данные, разметка или результаты с содержимым базы не входят в Git.

## Как проверить

Из корня, Python 3.11+; локально проверено на Python 3.12.10:

```sh
python3 -m unittest discover -s evaluation/rag -p 'test_*.py' -v
python3 evaluation/rag/benchmark.py --cases evaluation/rag/local/cases.json
```

20 тестов используют только вымышленные документы: загрузка ZIP/каталога,
UTF-8, лимиты, небезопасные пути, симлинки, таблицы, хвосты, fenced code,
нормализация, ранжирование, валидация, кэш, параллельные запросы,
работа четырёх плоских модулей без backend/frontend и сети, расчёт метрик.

Разметка `evaluation/rag/local/cases.json` остаётся локально, в Git её нет.
На другом компьютере сначала скачать базу и вопросы, затем создать свою разметку.
Схема одного элемента (синтетический пример, имена не из базы):

```json
[
  {
    "id": "invented-1",
    "query": "Как хранится фотография вымышленного макета?",
    "targets": [
      {"source": "example.md", "title": "Хранение", "contains": ["локально"]}
    ]
  }
]
```

`title` — подстрока заголовка/иерархии, `contains` — обязательные подстроки
текста с условиями. Проверяется, что размеченная цель существует в текущей базе.
Каждый target — отдельное требование: если нужно несколько разделов, перечислить
несколько targets. Критерий строгий: эквивалентный ответ из другого,
неразмеченного раздела может не засчитаться.

Подробный отчёт с запросами и найденными разделами сохраняется только в
`runtime/evaluation/rag-report.json`. В консоль идут агрегаты и ID пропусков.
Benchmark проверяет сохранность всех непустых строк тела документов, измеряет
построение, 30 повторов каждого поиска и пик Python-аллокаций через tracemalloc.
Последний показатель не равен полной памяти процесса/контейнера.

## Локальные результаты, 14.11.2026

Все 19 документов прочитаны: 233 уникальных фрагмента, 0 потерянных строк тела.
Размер с заголовками: минимум 106, медиана 426, максимум 4920 символов.

30 запросов: 18 demo-вопросов без изменений (включая полную историю пяти
диалогов) и 12 собственных запросов. Среди своих есть две вручную уточнённые
формулировки для проверки границы с ядром Платона. Это небольшой набор
разработки, не независимая оценка и не результат LLM-судьи.

| Метрика | Нормализация без синонимов | Нормализация + синонимы (по умолчанию) |
| --- | ---: | ---: |
| Хотя бы одна размеченная цель на первом месте | 8/30 | 10/30 |
| Хотя бы одна цель в первых трёх | 17/30 | 18/30 |
| Хотя бы одна цель в первых шести | 22/30 | 23/30 |
| Все размеченные цели в первых шести | 21/30 | 22/30 |
| MRR@6 по первой найденной цели | 0,441 | 0,497 |
| Медиана / p95 поиска, мс | 0,053 / 0,169 | 0,055 / 0,172 |

На 18 demo-вопросах вариант по умолчанию находит хотя бы одну цель в 14/18,
все отмеченные цели в 13/18. Полная переданная история — нагрузочный сценарий,
а не замена преобразованию диалога в запрос ядром Платона.

Создание retriever с чтением базы и записью кэша — около 32 мс,
с чтением существующего кэша — 29 мс. Пик Python-аллокаций при отдельном
построении — 1,67 МиБ. Времена относятся к локальному процессу без генерации,
не к SLA приложения; могут меняться между запусками.

## Ошибки и следующий эксперимент

- Пропущены все цели в 7/30 запросах; ещё в одном найдена только часть условий.
  Типовые ошибки: выбор общей справки вместо конкретной функции,
  отсутствие совпадающих слов у перефразировки, отвлечение на числовой показатель,
  неполное покрытие вопроса о нескольких продуктах или условиях.
- Цифра в запросе может поднять раздел про другой продукт. Специальные правила
  под отдельные demo-вопросы не добавлялись.
- Лексический поиск не проверяет допустимость задания: запрос про анекдот
  с упоминанием продукта возвращает документы. Нужен контроль области задачи
  в консультанте. Score не является вероятностью достоверного ответа.
- Не нужно добиваться 100% на этих demo-вопросах ручными соответствиями.
  Следующее обоснованное сравнение — BM25 против bge-m3 и гибрида (RRF),
  с сохранением этого набора и добавлением независимых перефразировок.
- API эмбеддингов, реранкер, общая генерация, CSV-сабмит и Docker-сценарий
  с поиском пока не проверены. Для сравнения нужны доступ к прокси и его
  документация; для интеграции — рабочее ядро консультации Платона.
