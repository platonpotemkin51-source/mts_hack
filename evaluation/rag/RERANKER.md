# Наш кандидат: гибрид + реранкер организаторов

Контроль — архив `submission-hybrid-evidence.zip`, сообщённый балл **61,664**.
Договорённость команды: одна попытка на наш поиск, одна на генерацию коллеги,
третья — на финальное объединение. Этот код не отправляет сабмиты.

## Что делает поиск

1. BM25 и BAAI/bge-m3 возвращают кандидатов; RRF объединяет позиции.
2. До 20 лучших кандидатов передаются на `/rerank`; запрашивается `top_n=TOP_K`
   (обычно 6). Имя модели — `RERANKER_MODEL`, иначе `qwen/qwen3-reranker-8b`.
3. Полученные индексы определяют новый порядок. Score — обратный ранг,
   а не старая оценка RRF и не вероятность достоверности.
4. После отбора добавляются недостающие ограничения и требования выбранных
   продуктов. Дополнительных embeddings или rerank-запросов для этого нет.

Ключ — `RERANKER_API_KEY` или ключ LLM; адрес тот же, что у генерации и embeddings.
Контракт взят из локального sample_submission.zip организаторов: query, documents,
top_n; ответ results или data с индексами. Сервис доступен только на платформе.

Один rerank-запрос на непустой вопрос, timeout 30 секунд. Ошибка сети, HTTP или
некорректные/повторные индексы дают предупреждение в stderr и возврат к исходной
гибридной выдаче. Данные и ключи в предупреждение не попадают. Повторов сервиса
в цикле нет. Ошибки embeddings по-прежнему не маскируются лексическим поиском.

## Проверки

- 100 backend/CSV + 69 RAG + 3 теста инструмента оценки = 172 теста.
- Проверены порядок индексов, оба формата ответа, отдельный ключ, top_n, timeout,
  недопустимые и повторные индексы, сбой HTTP/сети, сохранение baseline-порядка
  при ошибке, отсутствие утечки тела ответа и лишних запросов.
- Проверено сохранение ограничения продукта после rerank и один semantic-вызов.
- При искусственной недоступности rerank-сервиса те же 18 ID дважды обработаны
  без аварийных ответов; 36 предупреждений о fallback, тело ошибки не раскрыто.
- Распакованный кандидат прошёл все 18 demo-ID дважды через явно синтетические
  HTTP-transports: 0 аварийных ответов, 18 генераций на прогон, 36 rerank-запросов
  всего, не более 20 кандидатов; 15 пачек индекса + 36 query embeddings.
- На 30 локальных запросах с восстановлением истории контрольным consultant.py
  все ожидаемые текстовые признаки доступны в 25 случаях среди первых 6 BM25
  и в 28 среди первых 20. Это только проверка потенциала расширенного пула,
  не измерение качества настоящего гибрида или реранкера.

## Изоляция нашей попытки

```sh
python3 evaluation/rag/build_rerank_candidate.py
```

Скрипт требует SHA-256 контрольного архива
`23a0d691d098353f5b078b025b8ff70e4af41f196bd5be1f05200b479f8681ba`.
Он заменяет только retrieval.py и включает RERANK_ENABLED=1 в solution.py.
consultant.py, llm_client.py, chunking.py, contracts.py, kb_loader.py и зависимости
сохраняются побайтно. Поэтому последние локальные изменения диалога в нашу
попытку не попадут. Полные документы и переписывание запроса моделью не включены.

Выход: `runtime/submission-hybrid-rerank.zip`. Манифест с хешами и перечнем
неизменённых файлов: `runtime/evaluation/rerank-candidate-manifest.json`.
Секретов, базы и индексов в ZIP нет. Контрольный архив сохранён.

Для будущего объединения кода с коллегой общая сборка поддерживает:

```sh
python3 scripts/build_submission.py --retrieval-mode hybrid --rerank
```

Без флага реранкер отключён. Его нужно включать в финальной сборке по результату
нашей попытки, а не автоматически. Переменные платформы имеют приоритет перед
значениями по умолчанию в кандидате.

## Что остаётся неизвестным

Настоящие оценки Qwen3 Reranker 8B, его задержка и влияние на конкурсный score
локально недоступны. Имитация API этого не доказывает. Не гарантируются ни рост
с 61,664, ни достижение 70. Если платформа предоставит логи, проверить предупреждения
`using hybrid ranking without reranker`: они означают, что реального rerank не было.

## Дополнительное усиление перед нашей единственной попыткой

Проверка доступности Groq не дала работающего реранкера: `/reranking` принимает
запрос, но проверенные модели возвращают отсутствие доступа; настоящий ранкер
организаторов по-прежнему проверяется только на платформе.

Найдена конкретная потеря сведений о сочетании продуктов. Для явно смешанного
сбора данных (фотографии и подключённые/ручные приборы) теперь добавляется один
короткий раздел, прямо описывающий дополнение выбранных продуктов и содержащий
ссылку между их документами. Ссылка разрешается только среди уже загруженных
продуктов; сеть и файловая система по ссылке не читаются. Ограничение — один
целый фрагмент до 1000 символов. Обычные ссылки навигации не считаются такой связью.

На прежних 30 запросах с неизменным восстановлением истории полное покрытие
ожидаемых текстовых признаков: **28/30 → 29/30**. Все ранее найденные ID сохранились;
изменился ровно один контекст, +624 символа; медиана объёма не изменилась.
Это старый набор разработки и проверка доступных доказательств, не скрытый тест.

На этом целевом диалоге выполнены две генерации Groq 20b с одинаковыми настройками
и неизменным consultant.py контроля. После добора модель явно описала сочетание
подключённых приборов и фотографий вместо выбора одного способа; исчезло одно
неподтверждённое требование подготовки обучения. Однако повторный запрос уже
известных данных и служебные ID в тексте остались. Ручная проверка одного случая
не доказывает общего выигрыша и не воспроизводит оценку Qwen. Полные запросы
и ответы остаются в runtime/evaluation/relationship-answer-check.json.

Также поддержаны строковые целочисленные индексы rerank (`"0"`, `" 2 "`), как в
примере организаторов с int(item['index']). Дроби, bool и повторные индексы
по-прежнему отклоняются. Это устраняет потенциальный ненужный fallback.

После дополнения: 100 backend/CSV + 75 RAG + 3 теста инструмента = 178 тестов.
Проверены отсутствие добавления связи для вопросов о цене, персональных данных
и одного продукта; внешние/неизвестные ссылки; слишком большой фрагмент;
неизменность исходной выдачи и точность добавляемого текста.
