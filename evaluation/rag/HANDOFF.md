# Платону: три варианта поиска

Одна точка входа, общий `KnowledgeChunk`, одинаковая база и нарезка.
Меняется только переменная `RETRIEVAL_MODE` до вызова `build_retriever`.
Уже созданный объект режим не меняет. Backend/ядро консультации используют его
обычным `retrieve(query, top_k=6)`.

| Режим | Что делает | Когда пробовать |
| --- | --- | --- |
| `bm25` | Нормализованные слова, числа, аббревиатуры и синонимы | Базовый вариант, работа без сети |
| `embeddings` | Полные фрагменты и запрос через bge-m3, сортировка по cosine | Проверка бытовых перефразировок |
| `hybrid` | До 20 кандидатов каждого метода, равновесный RRF с константой 60 | Моя первая гипотеза для итогового варианта; победа ещё не доказана |

Гибрид не требует реранкера или дополнительной генеративной модели. Для него
используются те же векторы документов, что для `embeddings`. Сырые BM25 и cosine
score не складываются: RRF суммирует `1 / (60 + rank)` по двум спискам.
Если `top_k > 20`, каждый метод отдаёт как минимум `top_k` кандидатов.

## Подключение

Пример, общий для трёх режимов:

```python
from pathlib import Path
from retrieval import build_retriever

# Если режим нельзя задать окружением запуска, выбрать его явно в адаптере:
# import os; os.environ["RETRIEVAL_MODE"] = "hybrid"
retriever = build_retriever(Path("data/knowledge-base.zip"), Path("runtime/index"))
chunks = retriever.retrieve("Уточнённый запрос с учётом диалога", top_k=6)
```

Новые настройки, которые Платону нужно добавить в общую конфигурацию при интеграции:

```dotenv
RETRIEVAL_MODE=bm25
EMB_MODEL=baai/bge-m3
```

Для `embeddings`/`hybrid` нужны адрес и служебный ключ прокси в переменных
`LLM_BASE_URL`, `LLM_API_KEY` либо `OPENAI_BASE_URL`, `OPENAI_API_KEY`.
Как в примере организаторов, также поддерживаются `BASE_URL` и необязательный
`EMBEDDER_API_KEY`. Заглушки вида `LLM_BASE_URL=LLM_BASE_URL` считаются незаполненными.
Платформа подставляет доступ автоматически; собственные ключи для проверки не нужны.
Режим BM25 не требует этих переменных.

Импорты и создание `OrganizerEmbedder` не вызывают сеть. Построение сетевого
retriever без кэша вызывает embeddings для всех фрагментов; последующие запросы
делают embeddings только для поискового текста. Объект создаётся один раз,
синхронные вызовы выносятся из event loop. Каждый вызов владеет отдельным HTTP-клиентом;
общий индекс read-only, допускает параллельный поиск. Генерации ответов здесь нет.

## Точный HTTP-контракт

Проверен по `solution.py` внутри
[sample_submission.zip организаторов](https://drive.google.com/file/d/1iMSDN115sFiTOtZ3__PD0-bU5OgxSRv6/view):

```text
POST {LLM_BASE_URL}/embeddings
Authorization: Bearer {LLM_API_KEY}
{"model": "<EMB_MODEL>", "input": ["полный фрагмент", "ещё фрагмент"]}

{"data": [{"index": 0, "embedding": [0.1, 0.2]}, ...]}
```

`/v1` не добавляется. Векторы упорядочиваются по `index`, нормируются;
пропущенный index означает позицию элемента, как в примере организаторов.
Проверяются число, уникальность индексов, размерность, конечные числовые значения
и ненулевая норма. Размер пакета — 16 текстов, тайм-аут — 30 секунд,
максимум две попытки на пакет. Повторяются только транспортные ошибки, 429 и 5xx
с паузой 0,5 секунды. 401/403 не повторяются. Редиректы не выполняются.

При ошибке `EmbeddingError` нет скрытого перехода на BM25. Для такого перехода
нужно явно перестроить retriever с `RETRIEVAL_MODE=bm25` и показать режим разработчику.
Тексты ответов прокси и ключи в сообщения об ошибках и логи не попадают.

Кэш документов ключуется по ID всех фрагментов, модели, адресу прокси и версии
формата. JSON пишется атомарно. Повреждённый кэш перестраивается с предупреждением.
Смена модели/базы/прокси создаёт другой кэш. Если провайдер обновил веса под тем же
именем, кэш нужно удалить вручную; одну лишь смену весов определить нельзя.
Кэш экономит вызовы для документов, но запрос по-прежнему требует доступного API.
В нём нет ключа API; хранить кэш только локально в игнорируемом `runtime/`.

## Как сравнить, не расходуя сабмиты

При доступном прокси из корня проекта (зависимости из общего requirements):

```sh
python3 evaluation/rag/compare.py --questions data/questions.csv
```

Если настройки локально лежат в `.env`, можно добавить `--env-file .env`.
Этот флаг использует уже имеющийся `python-dotenv`; значения среды имеют приоритет.
Без флага файлы с ключами автоматически не читаются. На платформе флаг не нужен.

Скрипт выполняет каждый вопрос **один раз в каждом режиме**, повторно использует
кэш векторов между embeddings/hybrid, сохраняет запросы, источники, тексты и
задержки в `runtime/evaluation/rag-comparison.json`. Генерация не вызывается.
Вопросы с историей передаются как есть: для оценки на запросах ядра можно подготовить
локальный CSV `id,question` с его уточнёнными формулировками.

Без ручной разметки метрики качества равны `null`, а не фиктивным нулям или успехам.
Можно сравнить вручную найденные доказательства. Для автоматической проверки
размеченных разделов и обязательных оговорок:

```sh
python3 evaluation/rag/compare.py --cases evaluation/rag/local/cases.json
```

Разметка закрытая и не входит в Git; её схема описана в README. Ошибка одного
режима записывается как `status=error`, остальные режимы продолжаются. Если хоть
один режим завершился ошибкой, код выхода скрипта — 1.
Для автономной проверки без прокси: `--modes bm25`.

Если прокси доступен только во время автоматической проверки, локальное сравнение
модельных вариантов невозможно. Тогда Платон выбирает режим перед построением
retriever в своём `solution.py` и проверяет варианты отдельными сабмитами;
они расходуют попытки команды. `compare.py` — локальный инструмент, не точка
входа конкурсного ZIP. Основной сабмит по-прежнему использует плоские корневые
модули и `solution.py` Платона. Прогон сравнений или сабмитов здесь не выполнялся.

Технические тесты всех режимов:

```sh
python3 -m unittest discover -s evaluation/rag -p 'test_*.py' -v
```

Реальный сервис организаторов и качество bge-m3/гибрида пока не проверены.
HTTP-фикстуры проверяют интеграционный код, не способность модели понимать смысл.
У cosine/RRF нет настроенного порога отказа: ближайшие фрагменты могут оказаться
нерелевантными. Проверка достаточности доказательств остаётся в консультанте.
Весь запуск вместе с генерацией должен быть отдельно измерен в лимите 20 минут.
