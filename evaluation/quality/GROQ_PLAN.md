# Пять экспериментов качества через Groq

Статус: серия выполнена; результаты, принятые изменения и ограничения — в
[GROQ_RESULTS.md](GROQ_RESULTS.md). Ниже сохранён исходный план экспериментов.

Контроль текущего кода: `c00f658`, `ANSWER_REVIEW=0`. Публичный контроль команды:
`87497c7` (сообщённый результат 0,5752). Groq `openai/gpt-oss-120b` — инструмент
разработки, не замена конкурсной Qwen и не официальный LLM-судья.

## Сначала измерить существующие варианты

Создать 24 собственных сценария с вымышленными материалами: 16 для разработки,
8 отложить до выбора кандидата. До запуска зафиксировать необходимые факты,
условия, запретные обещания и ожидаемый следующий шаг. Покрыть одиночные вопросы,
диалоги, исправления, недостаток информации, числа/единицы и переход к заявке.
Короткий пилот: 6 случаев × два варианта = 12 основных генераций, без массового
перебора; дополнительные проверочные вызовы считать отдельно.
Новые вызовы в рамках составления этого плана не выполнялись.

Проверять итоговый `answer` после всего обработчика, а не только сырой текст.
Сохранять локально запрос поиска, найденные источники, сырой ответ и финальный
результат, время, токены, подстановки и причины отказов. Ключ не записывать.
Закрытая база остаётся в локальных проверках retrieval, во внешний Groq для этой
серии передавать только вымышленные данные. Не включать платные тарифы/автопополнение.

## Приоритеты

1. **Проверка и ремонт ответа.** Сначала A/B уже готового `ANSWER_REVIEW=0/1`.
   Если сигнал риска слишком узкий, расширить на утверждения о совместимости и
   перенос условий между продуктами, не переводя каждый ответ в два вызова.
   Принять при уменьшении неподтверждённых утверждений без увеличения ложных
   отказов; отдельно учесть задержку и долю неуспешных проверок.

2. **Поиск из реального смысла диалога.** На неоднозначных продолжениях сравнить
   нынешние лексические правила с одним условным переписыванием запроса моделью:
   текущая задача + актуальные параметры + последняя потребность. Факты из
   ассистентских реплик не считать подтверждёнными клиентом, не придумывать
   параметры. Принять при улучшении полноты конечного ответа на диалогах, не
   только при попадании документа; простые вопросы не должны получать лишний вызов.

3. **Отбор достаточных доказательств.** Сравнить текущий добор с выбором из
   кандидатов по конкретному вопросу: ответ по существу, применимость, важное
   ограничение. Убирать дубли/общие обзоры, сохраняя целые связанные условия.
   Не увеличивать TOP_K вслепую. Принять при меньшем числе потерянных оговорок
   и неуместных рекомендаций, с контролем объёма контекста. Работа embeddings
   организаторов от наличия ключа Groq автоматически доступной не становится.

4. **Короткий контракт генерации по задаче.** Для обычной консультации уменьшить
   обязательную служебную часть JSON и инструкции по извлечению цитат; для
   перехода к менеджеру сохранить контакты, потребность и содержательное резюме.
   Не убирать заявку/резюме из оценки и не менять контракт веба незаметно.
   Принять при уменьшении ошибок формата/обрывов и улучшении полноты ответа,
   без регрессии сценариев заявки. Это эксперимент, не заранее выбранный формат.

5. **Предметный переход к менеджеру.** Из фактических сведений клиента составлять
   1–2 предложения: основная потребность, актуальный объект/оборудование,
   существенные неизвестные. Не включать все обсуждавшиеся продукты в заявку.
   Спрашивать только недостающий контакт, не повторять известное и не обещать
   отправку до сохранения. Принять при лучшем выполнении сценариев с отказом,
   сменой потребности, передачей контакта и исправлением параметров.

## Как выбирать победителя

Фиксировать коммит, модель и одинаковые настройки. Изменять один фактор.
Сначала проверять обязательные факты, условия и запреты по ручной разметке.
Затем делать слепое попарное сравнение финальных текстов; спорные пары повторять
с обратным порядком A/B и проверять вручную. Судья на той же модели может иметь
общие с генератором ошибки и предпочитать длинные ответы — это не независимая истина.
Отложенные 8 случаев не использовать для настройки, при повторном использовании
перестать называть их независимой проверкой.

Не складывать локальные показатели в выдуманный «официальный score». Отдельно
показывать долю полноценных ответов, выдуманные факты/обещания, утраченные условия,
лишние отказы, повторные вопросы, качество заявки, задержку и число вызовов.
После отбора — один проверенный ZIP и реальная оценка Qwen на платформе;
улучшение Groq само по себе не доказывает рост лидерборда.
