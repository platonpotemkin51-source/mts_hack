# МТС Energytool — ИИ-консультант

Помогаем посетителю сайта описать задачу в энергетике, разобраться в подходящих продуктах Energytool и сформировать содержательную заявку менеджеру. Ответы опираются на предоставленную базу знаний, а сведения об объекте — на диалог с клиентом.

**Статус:** подготовлена структура проекта, контракты и задания трём участникам. RAG, генерация, чат, хранение истории, сбор заявки и конкурсный сабмит пока не реализованы. Сервер содержит только служебный маршрут `/api/health`.

## С чего начать

1. Прочитать [суть проекта](docs/PROJECT.md), [контракты](docs/CONTRACTS.md) и [правила работы](AGENTS.md).
2. Переключиться на свою ветку и передать Codex соответствующий файл задания.
3. Выполнить первый этап своего задания; затем объединить три части и пройти общий сценарий из [плана интеграции](docs/INTEGRATION.md).

| Участник | Ветка | Зона ответственности | Задание агенту |
| --- | --- | --- | --- |
| Платон | `dev/Platon` | Backend, LLM, история, заявки, интеграция, сдача | [PLATON.md](docs/tasks/PLATON.md) |
| Артём | `dev/Artem` | Загрузка базы, фрагменты, поиск, качество RAG | [ARTEM.md](docs/tasks/ARTEM.md) |
| Даниил | `dev/Daniil` | Vue-интерфейс, карточка клиента, отладка, сценарий демо | [DANIIL.md](docs/tasks/DANIIL.md) |

`main` — общая стабильная основа. Все три ветки участников начинаются с одного коммита. Отдельная ветка `dev` не требуется.

После публикации основы каждый участник клонирует репозиторий отдельно и выбирает свою ветку:

```powershell
git clone https://github.com/platonpotemkin51-source/mts_hack.git
Set-Location mts_hack
git fetch origin
git switch dev/Platon
```

Артём использует `git switch dev/Artem`, Даниил — `git switch dev/Daniil`. Если клон уже существует, повторный `git clone` не нужен. После коммита своей части: `git push -u origin HEAD`; затем PR в `main` для интеграции Платоном.

## Запуск служебного каркаса

Нужны Docker и Docker Compose. Из корня репозитория:

```powershell
Copy-Item .env.example .env
docker compose up --build
```

Доступны `http://localhost:8000/api/health` и `http://localhost:8000/docs`. В интерактивной документации сервера пока присутствует только health-маршрут. `contracts/openapi.json` описывает целевой API, который предстоит реализовать.

Backend локально без Docker (Python 3.11):

```powershell
py -3.11 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m uvicorn backend.app.main:app --reload --port 8000
```

Frontend пока не запускается: его создаёт Даниил в `frontend/`. После интеграции Платон добавляет frontend в Compose; итоговый продукт должен запускаться одной Docker-командой.

## Переменные окружения

Полный пример — [.env.example](.env.example).

| Переменная | Назначение |
| --- | --- |
| `LLM_BASE_URL` / `OPENAI_BASE_URL` | Адрес OpenAI-совместимого прокси |
| `LLM_API_KEY` / `OPENAI_API_KEY` | Ключ к прокси; не включается в Git и логи |
| `LLM_MODEL` / `OPENAI_MODEL` / `GEN_MODEL` | Идентификатор модели из среды; не фиксируется в коде |
| `DATA_DIR` | Каталог `questions.csv` и `knowledge-base.zip`; по умолчанию `data` |
| `TEMPERATURE`, `MAX_TOKENS`, `MAX_WORKERS` | Параметры генерации и параллельности |
| `TOP_K`, `CHUNKER`, `EMB_MODEL`, `RERANKER_MODEL`, `RERANKER_TOP_N` | Параметры поиска |
| `SQLITE_PATH`, `CACHE_DIR`, `CORS_ORIGINS` | Локальное хранение, индекс и разрешённые origin интерфейса |

При проверке организаторы предоставляют модель Qwen3.8-27B через прокси и передают настройки среды. Контракт подключения реализует Платон. Для локального прототипа выбранный сервис, модель и порядок получения доступа нужно дополнить после подключения; рабочих ключей в каркасе нет.

## Данные и ограничения

Исходные материалы кейса, вопросы, эталонные ответы, их копии и извлечённые фрагменты **не публикуются в открытом репозитории**. Скачивание выполняется участником локально по [исходным ссылкам](docs/SOURCES.md). В `data/` отслеживается только инструкция.

Демонстрационные данные в `frontend/mocks/` придуманы командой и не являются рекомендацией о реальных продуктах. Заявки в прототипе используют только выдуманные персональные данные. Реальная отправка в CRM, почту или менеджерам не нужна.

## Проверка и сдача

- [Чек-лист интеграции и приёмки](docs/INTEGRATION.md).
- [Правила конкурсной упаковки](docs/SUBMISSION.md).
- `python scripts/build_submission.py` собирает исходный каркас в `runtime/submission-scaffold.zip`. **Этот архив пока нельзя сдавать:** `solution.py` намеренно завершится с сообщением о незавершённой реализации.
- Зависимости Python закреплены версиями из опубликованного организаторами списка. Lock-файл frontend добавляет Даниил.

Ограничения каркаса: нет консультации, поиска, UI, сохранения сессий, заявок и генерации `submission.csv`; Docker и обращения к модели требуют отдельной проверки после реализации. Наличие структуры не означает готовности к оценке.
