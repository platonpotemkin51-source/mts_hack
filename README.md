# Energytool — ИИ-консультант

Веб-консультант помогает выбрать решение Energytool по предоставленной базе знаний,
уточняет задачу клиента и сохраняет заявку с резюме для менеджера. Чат, карточка
клиента, архив всех разговоров и режим отладки работают в одном интерфейсе.
Реальной отправки в CRM или почту нет. Контакты в демонстрации — вымышленные.

## Запуск

Нужны Docker Engine с Compose v2.24.4+ (или Docker Desktop), интернет для сборки и
доступ к OpenAI-совместимому API генерации.

1. Скопируйте `.env.example` в `.env` (`cp .env.example .env` в macOS/Linux).
2. Заполните `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`.
3. Поместите предоставленную базу в `data/knowledge-base.zip`. В ZIP должны быть
   Markdown-файлы UTF-8. Исходная база не распространяется с репозиторием.
4. Запустите из корня:

```sh
docker compose up --build -d
```

Откройте [чат](http://localhost:5173). [API](http://localhost:8000/docs),
[готовность](http://localhost:8000/api/ready).
Порты привязаны к localhost: сервис предназначен для локальной демонстрации.

`docker compose logs --tail=50` — журнал; `docker compose ps` — состояние;
`docker compose down` — остановка. Именованный том `app-data` сохраняет архив и
индекс после остановки. **`docker compose down -v` удаляет архив и заявки.**
После изменения `.env` или базы перезапустите `docker compose up -d --force-recreate`.
Healthcheck готовности проверяет загрузку базы и наличие настроек, но не вызывает
модель. Неверный ключ обнаружится при первом сообщении как 503.

## Внешние API и настройки

Ключ используется только backend; в браузер и Docker-образ он не попадает.
Адрес API указывается целиком, например `https://api.groq.com/openai/v1`.
`/v1` автоматически не добавляется. Провайдер получает историю и найденные
фрагменты базы: используйте только разрешённый командой сервис.

| Переменная | Назначение / значение по умолчанию |
| --- | --- |
| `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` | Обязательные адрес, ключ и имя модели |
| `RETRIEVAL_MODE` | `bm25` для Groq; `hybrid` при доступных embeddings |
| `EMB_MODEL` | `BAAI/bge-m3`; имя должно поддерживаться вашим провайдером |
| `EMBEDDER_API_KEY` | Необязательный отдельный ключ embeddings на том же base URL |
| `TOP_K` | 6 основных фрагментов, дополнительно добираются существенные ограничения |
| `TEMPERATURE`, `MAX_TOKENS` | 0.2 и 2048 |
| `SESSION_IDLE_MINUTES` | 60; неактивный разговор закрывается и остаётся в архиве |
| `UI_PORT`, `API_PORT` | 5173 и 8000 на localhost |
| `CORS_ORIGINS` | Разрешённые адреса UI; изменить при смене UI-порта |

Groq: создайте ключ в кабинете провайдера, внесите его в `LLM_API_KEY` и выберите
доступную вашему аккаунту модель в `LLM_MODEL` (пример — `openai/gpt-oss-120b`).
Groq не предоставляет нужные embeddings: оставьте `RETRIEVAL_MODE=bm25`.
Гибрид требует API `{LLM_BASE_URL}/embeddings` с поддержкой `EMB_MODEL`.
Организаторский доступ предоставляется платформой и локально у команды отсутствует.
Compose фиксирует внутренние пути `/app/data` и `/app/runtime`, независимо от
локальных `DATA_DIR`, `CACHE_DIR`, `SQLITE_PATH`.

## Архитектура

```text
Браузер → nginx / Vue → FastAPI → Consultant → поиск → модель API
                          ↓           ↑       ↑
                        SQLite      история   Markdown ZIP
```

| Код | Ответственность |
| --- | --- |
| `frontend/src/` | Чат, карточка, форма заявки, архив, источники и время |
| `backend/app/main.py` | HTTP-валидация, ошибки, сессии и координация запросов |
| `backend/app/storage.py` | Транзакции SQLite, история, заявки, идемпотентные повторы |
| `energytool/consultant.py` | История, поисковый запрос, промпт, проверка ответа и карточка |
| `energytool/kb_loader.py`, `energytool/chunking.py` | Безопасное чтение ZIP и нарезка по заголовкам |
| `energytool/retrieval.py` | BM25 / embeddings / гибрид RRF, добор ограничений продуктов |
| `energytool/llm_client.py` | Тайм-ауты, ограниченные повторы и безопасные ошибки API модели |
| `energytool/contracts.py`, `contracts/openapi.json` | Доменные типы и опубликованный HTTP-контракт |
| `solution.py` | Конкурсный CSV через то же ядро, отдельный контекст каждого ID |

Ядро находится в пакете `energytool/`, HTTP-адаптер — в `backend/`, UI —
в `frontend/`, проверки — в `evaluation/`. В корне оставлена точка входа
`solution.py` для CSV. Сборщик отдельно преобразует импорты
и формирует плоский ZIP по требованиям платформы. Backend и frontend
отделены от ядра и не импортируются им. Индекс переиспользуется, состояние клиента
хранится отдельно в SQLite. Один backend-процесс — согласованная запись диалога.

Функциональная основа восстановлена из **hybrid-evidence, 61.664**; происхождение
и результаты экспериментов — [BEST_SUBMISSION](evaluation/rag/BEST_SUBMISSION.md).
Удачный платформенный запуск использовал гибрид, а локальный Groq — BM25.
Это разные конфигурации; балл 61.664 не относится к локальному режиму.
Реранкер и поздние изменения генерации не включены.

## Проверка сценария

1. Напишите задачу, например «Нужен учёт электроэнергии на складе».
2. Ответьте на уточнение. Проверьте, что карточка обновилась, а контекст сохранился.
3. Включите «Отладка» перед следующим сообщением: откройте «Источники и время».
4. Откажитесь от контактов — консультация должна продолжиться. Затем нажмите
   «Оформить заявку», внесите вымышленные ФИО, телефон, компанию и согласие.
5. Сохраните заявку; проверьте серверное резюме и его скачивание в архиве.
6. Создайте новый диалог: карточка чистая, прошлый разговор доступен в архиве,
   в том числе разговор без заявки. Обновите страницу и проверьте архив снова.

Автоматические проверки (Python 3.11+, Node 22+, установленный Chrome для UI):

```sh
python3 -m pip install -r requirements.lock
python3 -m unittest discover -s evaluation/backend -p 'test_*.py'
python3 -m unittest discover -s evaluation/rag -p 'test_*.py'
cd frontend
npm ci
npm run build
npm test
```

Тесты используют синтетические данные и не требуют API-ключа.
Полный Docker smoke: `python3 scripts/smoke_docker.py` (порты 5187/8187;
создаёт и удаляет только отдельный проект energytool-check с его тестовым томом).
Python закреплён полностью в requirements.lock; Node — в package-lock.json.
[Проверки и ограничения](docs/VERIFICATION.md), [безопасность](docs/SECURITY.md).
Для разработки: `python3 -m uvicorn backend.app.main:app --env-file .env`,
в другом терминале `cd frontend && npm run dev`.

## Ограничения и сдача

Факты о продуктах берутся только из базы; параметры клиента — из диалога.
Если сведений не хватает, бот должен уточнить задачу или предложить специалиста.
Промпт и проверки снижают риск выдумок, но не доказывают истинность каждого ответа.
Ориентир — до 150 слов; подробный ответ допустим по задаче, CSV — до 10 000 символов.
Техническая настройка приборов не входит в консультацию. Лимиты внешнего API могут
увеличивать задержку; ошибки не выдаются за успешные ответы.

Авторизации нет: любой имеющий доступ к серверу видит общий архив. Для публичного
сайта нужны контроль доступа, HTTPS, политика хранения и согласования обработки
данных. Не публикуйте порты за пределами localhost без этих мер.
Не коммитьте `.env`, базу, диалоги, индексы и исходные CSV организаторов.

Для автоматической платформы: положите `questions.csv` и `knowledge-base.zip` в
`data/`, настройте API и запустите `python3 solution.py`. Он создаст `submission.csv`.
`python3 scripts/build_submission.py` собирает отдельный плоский ZIP с гибридом;
загрузка на платформу выполняется вручную ответственным участником.

Для финальной сдачи нужен репозиторий и PDF-презентация либо ZIP с кодом и PDF.
[Текущая презентация](docs/energytool-presentation.pdf) сохранена; перед защитой
команде нужно сверить её с финальной версией. Для приватного репозитория владелец
предоставляет жюри `hack-and-change-2026` доступ. Правила: [SUBMISSION](docs/SUBMISSION.md).
