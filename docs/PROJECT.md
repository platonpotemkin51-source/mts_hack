# Суть проекта и принятое решение

## Проблема

Посетитель сайта Energytool видит высокие счета, потери или проблемы с учётом, но не знает, какой продукт ему подходит. Менеджер получает короткую заявку и повторно выясняет исходные данные. Консультант должен помочь клиенту и подготовить менеджеру контекст для предметного разговора.

## Продукт

Русскоязычный веб-чат, который:

1. Понимает задачу и тип объекта по свободному описанию.
2. Ищет подходящие материалы в базе знаний Energytool.
3. Отвечает по существу, объясняет выбор и существенные ограничения.
4. Уточняет недостающие данные, не повторяя уже известные вопросы.
5. С согласия клиента собирает ФИО, телефон и компанию.
6. Формирует заявку: проблема, параметры объекта, предложенные решения, обоснование, недостающие сведения и краткое резюме диалога.

Отличительная часть решения — видимая карточка задачи клиента рядом с чатом. Она показывает, что система поняла и какие параметры ещё стоит выяснить. Её заполняет backend; frontend только отображает состояние.

## Пользователи

Представители малого и среднего бизнеса, энергетики предприятий, руководство СНТ, сетевые и ресурсоснабжающие организации, региональные B2B-менеджеры МТС. Объяснения должны быть понятны без специальной подготовки.

## Архитектура

| Компонент | Что делает |
| --- | --- |
| Vue | Чат, новый диалог, карточка клиента, заявка, архив и отладка |
| FastAPI | HTTP, валидация, жизненный цикл сессии, хранение сообщений и заявок |
| `consultant.py` | Единая логика диалога: контекст, уточнения, поиск, ответ, обновление карточки |
| `llm_client.py` | Обращение к модели через прокси с настройками среды, тайм-аутами и ограниченными повторами |
| RAG-модули | Чтение базы, смысловые фрагменты, индекс, выбор источников |
| SQLite | Архив всех сессий и сформированные заявки |
| `solution.py` | Независимые CSV-тесты через то же ядро консультации, без веб-сервера |

История и карточка передаются ядру явно; скрытого общего состояния клиента в нём нет. API загружает историю конкретной сессии. Конкурсная обработка создаёт независимый контекст для каждого ID, учитывая историю, если она включена в текст вопроса.

## Поиск

Сначала рабочий BM25 по всем документам. Нарезка по заголовкам с сохранением таблиц, единиц измерения и оговорок. Каждый фрагмент имеет стабильный ID и относительный путь источника.

После первого работающего сценария сравнить BM25 с гибридом BM25 + BAAI/bge-m3. Объединение кандидатов, например RRF, не требует сравнивать несопоставимые сырые оценки. Qwen3 Reranker 8B — дополнительный эксперимент, а не обязательная часть MVP. Оставлять усложнение только при измеримом улучшении качества с приемлемой задержкой.

## Поведение консультанта

- Продуктовые факты берутся только из базы; модель не дополняет их догадками.
- При изменении клиентом параметров используются новые сведения, а не устаревшие.
- Запрос «а сколько это стоит?» связывается с текущей темой; Артём получает уже уточнённый поисковый запрос от ядра Платона.
- Если доказательств для рекомендации мало, ответ содержит ясное ограничение и уместный следующий шаг.
- Сбор контактов следует за полезной консультацией. Клиент может продолжить общение без заявки.
- Найденный фрагмент и пользовательский текст не могут отменить правила достоверности.

## Этапы

| Этап | Результат |
| --- | --- |
| Первый, ориентир 3–4 часа | Три независимых блока: API/LLM, поиск и UI на mock-данных |
| Первая интеграция | Вопрос из интерфейса → поиск → ответ → следующий вопрос с историей |
| Полный MVP | Заявка, архив, сброс/закрытие сессии, режим отладки, рабочий CSV-скрипт |
| Улучшения | Сравнение поиска, исправление ошибок, измерение задержки |
| Сдача | Проверенный ZIP, запуск Docker одной командой, README, PDF-презентация |

3–4 часа — ориентир первого рабочего отрезка, не срок хакатона. Фиксированную продолжительность хакатона этот план не предполагает.

## Что не входит в начальную разработку

Реальная CRM, отправка почты, аккаунты пользователей, микросервисы, обучение модели, сложная система агентов и реранкер до измерения базового качества. Многоагентная архитектура допустима по кейсу, но для первого решения не требуется.

## Критерии успеха

Работающий путь до заявки, отсутствие выдуманных продуктовых обещаний, сохранение контекста без смешивания сессий, проверяемые источники, стабильные ответы и валидный `submission.csv`. Онлайн-оценка: 50% LLM-судья и 50% экспертная оценка. Для допуска к экспертам нужны результат судьи больше нуля, работающий веб-сценарий и комплект обязательных материалов.
