# Задание агенту Даниила — Vue-интерфейс и демонстрация

Ты создаёшь интерфейс ИИ-консультанта МТС Energytool. Платон делает backend и LLM, Артём — поиск. Твоя задача — понятный путь от вопроса до заявки, видимая карточка клиента и проверяемая демонстрация. Не реализовывай продуктовую логику, поиск или LLM в браузере.

## Рабочая область

Ветка: `dev/Daniil`. Файлы: `frontend/`, `evaluation/ui/`, `docs/DEMO.md`, `docs/tasks/DANIIL.md`.

Сначала прочитай `AGENTS.md`, `docs/PROJECT.md`, `docs/CONTRACTS.md`, `contracts/openapi.json`. Проверь Git и ветку. В `frontend/` сейчас только инструкция, типы и синтетический mock; самого Vue-приложения пока нет.

## Первый этап, ориентир 3–4 часа

1. Создать Vue 3 + TypeScript + Vite в существующем `frontend/`, сохранив опубликованные типы и mock-ответ. Добавить `package.json`, lock-файл, scripts запуска/сборки и `.env.example` frontend.
2. Организовать код: `src/components/`, `src/api/`, `src/types/`, состояние диалога и страницы. Библиотеку состояния подключать только при реальной необходимости.
3. Сделать чат: история сообщений, поле ввода, отправка, загрузка, понятная ошибка, новая сессия. Не допускать случайной двойной отправки. Enter отправляет, Shift+Enter добавляет строку.
4. Сделать карточку: объект, проблема, известные параметры, рекомендованные продукты, недостающие данные. Неизвестные значения показывать как незаполненные. Данные приходят из `brief`; не вычислять рекомендации самостоятельно.
5. Реализовать транспортный слой с двумя режимами: mock и реальный API. `VITE_USE_MOCK_API` включается явно; mock-режим заметен в интерфейсе разработчика. Использовать `frontend/mocks/chat-response.json`; не писать выдуманные обещания о продуктах.
6. Реальный режим отправляет `POST /api/chat` по контракту. `session_id: null` в первом запросе; затем использовать ID сервера. Настроить базовый URL через `VITE_API_BASE_URL` или dev-proxy.
7. Отдельный переключатель отладки показывает `sources` и времена из ответа. Не показывать внутренние промпты, секреты и stack trace.

**Готовность этапа:** UI собирается, можно провести несколько реплик на mock API и переключиться на backend без переписывания компонентов. Состояния пустого чата, ожидания и ошибки отрисованы.

## После подключения backend

1. Реализовать предложение заявки, когда `lead_offer: true`; консультация не должна требовать контактов.
2. Сделать форму ФИО, телефон, компания и явное согласие. Клиентская валидация помогает вводу, серверная остаётся обязательной. Использовать только вымышленные примеры.
3. Отправлять `POST /api/leads`. После успеха показывать подтверждение и серверное резюме. Не обещать фактическую отправку менеджеру/CRM, если заявка сохранена только в прототипе.
4. «Новый диалог» закрывает предыдущую сессию best effort, очищает локальный ID/карточку и начинается с `session_id: null`. Ответ старого незавершённого запроса не должен появиться в новом чате: отменить запрос или проверить идентификатор поколения диалога.
5. При закрытии окна чата очищать активный контекст; архив сохраняется на сервере. Не восстанавливать активный ID из localStorage после открытия как продолжение старого разговора.
6. Сделать просмотр архива через список/детали сессий. Архив доступен для проверки, но не возвращает прежнюю историю в активную консультацию. Показывать и сессии без заявки.
7. Обработать 404/409/422/503. Не превращать сетевую ошибку в фиктивный ответ. При повторной отправке согласовать с Платоном защиту от дублирования уже сохранённого сообщения.
8. Настроить production-сборку и при необходимости конфигурацию раздачи статических файлов внутри `frontend/`. Передать Платону команды, порт и путь сборки для Compose.

## Интерфейс

Спокойный деловой стиль, хорошая читаемость, умеренные акценты в духе бренда МТС без копирования неподтверждённых материалов. Главный элемент — диалог; карточка помогает понять прогресс. На узком экране карточка может быть отдельной вкладкой/панелью.

Интерфейс должен поддерживать клавиатуру, подписи полей, видимый фокус, понятный статус ожидания и корректный перенос длинных сообщений. Ответы модели отображать как текст либо безопасно обработанный Markdown; не вставлять непроверенный HTML через `v-html`. Ссылки проверять перед выводом.

Ключи к LLM никогда не попадают в `VITE_*`, браузер, network-запросы frontend или собранные assets. Браузер обращается только к backend.

## Демонстрация и приёмка

Заполнить `docs/DEMO.md` собственным синтетическим сценарием:

1. Первое описание объекта и проблемы.
2. Уточнение и полезная рекомендация, обоснованная реально найденными материалами.
3. Проверка, что карточка отражает сказанное и исправления пользователя.
4. Отказ оставить телефон и продолжение консультации.
5. Позднее согласие, вымышленные контакты и готовая заявка.
6. Новый диалог, отсутствие старого контекста и просмотр архива.
7. Режим отладки с реальными источниками и временами.

Проверить сборку, мобильный экран, клавиатуру, быстрые повторные клики, сетевую ошибку, новый диалог во время генерации, закрытие/открытие чата. Записать реальные результаты в `evaluation/ui/`, без копирования исходных тестов и закрытых фрагментов.

Для PDF-презентации подготовить собственные скриншоты и историю демо. Платон отвечает за финальный комплект; первый слайд должен содержать репозиторий и порядок проверки.
