# Задание агенту Артёма — база знаний и RAG

Ты отвечаешь за достоверный поиск по базе знаний МТС Energytool. Платон делает LLM, backend, заявки и конкурсный CSV; Даниил делает интерфейс. Твоя задача — дать Платону подходящие фрагменты со всеми существенными оговорками. Не генерируй финальные ответы, не создавай FastAPI, сессии и UI.

## Рабочая область

Ветка: `dev/Artem`. Файлы: `kb_loader.py`, `chunking.py`, `retrieval.py`, `evaluation/rag/`, `data/README.md`, `docs/tasks/ARTEM.md`.

Прочитай `AGENTS.md`, `docs/PROJECT.md`, `docs/CONTRACTS.md`, `contracts.py`, `docs/SUBMISSION.md`. Проверь Git и свою ветку. **Корневые модули не переносить в `rag/`: платформа требует плоский ZIP.**

## Первый этап, ориентир 3–4 часа

1. Скачать базу и demo-вопросы по ссылкам в `docs/SOURCES.md` в локальный `data/`. Убедиться, что Git их игнорирует. Не коммитить архивы, исходные тексты, вопросы, golden-ответы и индекс с содержимым базы.
2. Изучить все документы и структуру. Отдельно найти справочники, числовые условия, ограничения и связи продуктов. Не полагаться на первые символы файла и не исключать хвосты документов.
3. Реализовать `load_documents(kb_path)`: принимать ZIP или каталог, читать все Markdown-документы UTF-8. Отдавать `KnowledgeDocument` со стабильным ID и относительным `source`.
4. При ZIP безопасно читать выбранные текстовые entries без извлечения произвольных путей. Ограничить разумный размер чтения; не допускать записи за пределы каталога при распаковке, если она вообще нужна.
5. Реализовать `chunk_documents`: смысловая нарезка по заголовкам, сохранение таблиц, условий и единиц. Не отделять число от контекста применимости. Настроить размер и небольшое перекрытие, проверить вручную крупные разделы.
6. Реализовать BM25 по всем фрагментам с нормализацией русскоязычного текста, аббревиатур и чисел. Не требовать внешнюю генеративную модель для базового поиска.
7. Экспортировать `build_retriever(kb_path, cache_dir=None)` из `retrieval.py`. Объект поддерживает `retrieve(query, top_k=6)` и возвращает `list[KnowledgeChunk]` по общему контракту.
8. Проверить поиск на demo-вопросах и собственных перефразировках. Передать Платону рабочую сигнатуру, необходимые зависимости и пример локального вызова.

**Готовность этапа:** база полностью прочитана, индекс строится один раз, запрос возвращает не более `top_k` уникальных фрагментов с источниками, импорт модуля сам по себе не начинает сеть или индексирование.

## Контракт и крайние случаи

- Вход поиска — уже уточнённая Платоном формулировка. Историей клиента ты не управляешь.
- Поля: `chunk_id`, `source`, `title`, `text`, `score`. Форму не менять.
- `source` — относительный путь документа; ID стабилен для одинакового содержимого и правил нарезки.
- Пустой запрос/отсутствие подходящих данных — пустой список. Некорректный `top_k` — ясная ошибка валидации. Повреждённая или отсутствующая база — явная диагностическая ошибка, не выдуманные результаты.
- Сырые score разных методов не складывать как сопоставимые величины. Score не равен уверенности модели.
- Не возвращать одни и те же фрагменты несколько раз.
- Объект поиска будет переиспользоваться между запросами. Документируй потокобезопасность; не меняй историю/данные клиента.

## После первого BM25

1. Создать ручной набор оценки retrieval: вопрос → ожидаемый документ/раздел → важное ограничение. Исходные вопросы организаторов и фрагменты остаются локально; в Git допустимы свои синтетические формулировки без копирования базы.
2. Сравнить BM25 с эмбеддингами BAAI/bge-m3 и гибридом. Использовать тот же прокси и переменные доступа, что у LLM; схему запроса проверить по документации/рабочему примеру.
3. При объединении кандидатов использовать, например, RRF. Начать с 20 кандидатов и финальных 5–8 фрагментов как гипотезы; параметры выбирать по замерам.
4. Если нужен реранкер Qwen3 Reranker 8B, провести отдельное сравнение качества и задержки. Не включать его без доказанного выигрыша.
5. Обеспечить кэш индекса, привязанный к хешу базы, конфигурации нарезки и модели эмбеддингов. Не переиспользовать устаревший кэш молча.
6. Проверить холодный запуск, объём памяти и поведение без сети. BM25 может быть явно описанным fallback; не маскировать неработающие эмбеддинги как гибридный поиск.
7. Передать Платону итоговую конфигурацию и ограничения. Зависимости предложить списком; общий `requirements.txt` правит Платон.

## Что проверять особенно

Ограничения должны находиться вместе с преимуществами. После чтения реальной базы проверить, например, вопросы об автономности солнечной станции, интерпретации потерь и условиях выхода на разные модели энергоснабжения. Эти пункты — направления проверки, а не разрешение подставлять факты из памяти.

Также проверить синонимы, бытовые формулировки, аббревиатуры, числовые границы, запросы про несколько продуктов и вопросы вне базы. Зафиксировать, где нужный документ не найден и почему.

## Приёмка

- Поиск использует полное содержимое всех документов.
- Фрагменты сохраняют смысл, таблицы и условия числовых показателей.
- Источники и ID проверяемы, выдача без дублей.
- Импорт/вызов работает в плоском каталоге конкурсного ZIP без `backend`.
- Измерены время индексирования, медиана/p95 поиска и память хотя бы на локальном наборе.
- В итоговом отчёте есть сравнение вариантов, разобранные ошибки и известные пробелы.
- В Git нет исходных материалов, фрагментов и индекса с текстом базы.
