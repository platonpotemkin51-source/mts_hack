# Контракты интеграции, версия 1

Этот документ — договор команды. HTTP-схемы и статусы зафиксированы в `contracts/openapi.json`; Python-типы — в `contracts.py`. API реализован в `backend/app/main.py`.

## Граница поиска и консультации

```python
retriever = build_retriever(kb_path, cache_dir=cache_dir)
chunks = retriever.retrieve(query, top_k=6)
```

`build_retriever` экспортируется из `retrieval.py`. `kb_path` — путь к ZIP базы или распакованному каталогу. Возвращаемый объект реализует протокол `Retriever` из `contracts.py`.

Метод `retrieve` синхронный. Возвращает `list[KnowledgeChunk]`, отсортированный по убыванию релевантности; при отсутствии подходящих фрагментов — пустой список. Список содержит не более `top_k` элементов, без повторов `chunk_id`. Не использовать числовой score как калиброванную вероятность правильного ответа.

| Поле фрагмента | Тип | Смысл |
| --- | --- | --- |
| `chunk_id` | `str` | Стабильный ID внутри версии базы |
| `source` | `str` | Относительный путь Markdown-документа, без абсолютного пути компьютера |
| `title` | `str` | Название документа/раздела |
| `text` | `str` | Полный релевантный фрагмент с оговорками и единицами |
| `score` | `float` | Оценка текущего метода поиска |

Артём читает документы и строит индекс один раз. Платон создаёт поисковый запрос с учётом истории. Артём не вызывает генеративную LLM и не хранит клиентские сессии. Платон не дублирует индексирование. Потокобезопасность и возможные сетевые вызовы эмбеддингов описать в README своего модуля; FastAPI не должен блокировать event loop синхронным поиском.

## Граница ядра и адаптеров

```python
result = consultant.respond(message=message, history=history, brief=brief)
```

Ядро получает историю до текущего сообщения и текущую карточку. Возвращает `ConsultationResult`: ответ, найденные источники, обновлённую карточку, предложение заявки и измеренные времена. В нём нет FastAPI, SQLite, глобального клиента или скрытого `session_id`. Хранением и идентификаторами занимается API. Согласие и контактные данные проверяет отдельный обработчик заявки, а не текстовая догадка модели.

`answer_test_case` обрабатывает один CSV-вопрос без состояния предыдущего ID. Формат истории в `question` необходимо сверить с примером организаторов до реализации парсера.

## HTTP

| Метод и путь | Запрос | Успех | Назначение |
| --- | --- | --- | --- |
| `GET /api/health` | — | 200 `HealthResponse` | Состояние сервера |
| `GET /api/ready` | — | 200/503 `HealthResponse` | Готовность базы и настроек модели |
| `POST /api/sessions` | — | 201 `SessionSummary` | Создать новую сессию |
| `POST /api/chat` | `ChatRequest` | 200 `ChatResponse` | Ответить; при `session_id: null` создать сессию |
| `POST /api/sessions/{session_id}/close` | — | 200 `SessionSummary` | Закрыть сессию без удаления истории |
| `GET /api/sessions` | — | 200 `SessionSummary[]` | Список всех сессий для архива прототипа |
| `GET /api/sessions/{session_id}` | — | 200 `SessionDetail` | История и состояние; чтение не возобновляет сессию |
| `POST /api/leads` | `LeadRequest` | 201 `LeadResponse` | Сохранить заявку с резюме |
| `POST /api/requests/{request_id}/close` | — | 204 | Закрыть сессию потерянного запроса |

### Запрос чата

```json
{"session_id":null,"message":"Хочу обсудить энергоснабжение склада","debug":true,"request_id":"f6e3501b-3f08-4d51-997d-01d5dd012f2b"}
```

`message` — непустая после удаления пробелов строка. `session_id` — непрозрачная строка, которую возвращает сервер; frontend не генерирует её самостоятельно. `debug` по умолчанию `false`.
`request_id` — случайный ID новой реплики. При неопределённой ошибке повторяется тот же ID и текст. Сервер возвращает сохранённый ответ либо повторяет неуспешную генерацию без второго сообщения клиента. Запоздалый повтор после более новых сообщений даёт 409. Одновременно формируется не более одного ответа на сессию. Если поле отсутствует, сервер генерирует ID сам, но безопасный повтор без него невозможен.

### Ответ чата

```json
{
  "session_id": "demo-session",
  "answer": "Какую задачу на складе нужно решить в первую очередь?",
  "sources": [],
  "brief": {
    "object": "Склад",
    "problem": null,
    "known_parameters": [],
    "recommended_products": [],
    "missing_fields": ["Основная задача"]
  },
  "lead_offer": false,
  "debug": {"retrieval_ms": 0.0, "generation_ms": 0.0, "total_ms": 0.0}
}
```

Это синтетический пример формы, не результат реальной консультации. При `debug: false` поле `debug` равно `null`. `sources` использует форму `KnowledgeChunk`; тексты доступны для локальной отладки, не добавляются в Git. Промпты, ключи, служебные заголовки и stack trace не возвращаются.

### Сессии

`SessionSummary`: `session_id`, `status` (`active`/`closed`), `created_at`, `updated_at`. Время — ISO 8601 UTC. `SessionDetail` добавляет `messages`, `brief`, `lead_id`. Сообщение содержит `role` (`user`/`assistant`), `content`, `created_at`.

Неизвестная сессия даёт 404; отправка сообщения в закрытую — 409. Новая сессия всегда имеет пустую историю и карточку. Повторное закрытие существующей сессии допустимо и не удаляет историю. Архив включает сессии без заявки. Закрытие интерфейса и «Новый диалог» сбрасывают текущий ID на frontend, даже если запрос закрытия не успел завершиться.
При закрытии вкладки браузер отправляет закрытие по известному `session_id` или `request_id` ожидаемого ответа. Сервер не добавляет поздний ответ отменённого запроса. Если браузер не доставил закрытие, активная сессия закрывается после `SESSION_IDLE_MINUTES` бездействия (по умолчанию 60 минут), сохраняя архив. Генерацию, прерванную перезапуском, можно повторить с тем же `request_id`.

### Заявка

```json
{
  "session_id": "demo-session",
  "full_name": "Тестовый Клиент",
  "phone": "+70000000000",
  "company": "Демо-компания",
  "consent": true
}
```

Данные вымышленные, номер не используется для связи. Backend проверяет непустые поля, разумный формат телефона, активность сессии и `consent: true`. Резюме формируется на сервере из истории и карточки. Ответ: `lead_id`, `session_id`, `summary`, `created_at`. Передача менеджеру — сохранение внутри прототипа; реальной внешней отправки нет. Повторная заявка в той же сессии возвращает 409, чтобы двойной клик не создавал дубликаты.

### Ошибки

```json
{"error":{"code":"session_closed","message":"Начните новый диалог."}}
```

Предусмотрены 404, 409, 422 для валидации и 503 для временной недоступности модели/базы. Пользователь видит понятное сообщение. Ошибка не становится фиктивным успешным ответом. Прежняя переписка сохраняется. `GET /api/ready` сообщает о наличии базы и настроек модели, но не делает пробный вызов прокси.

## Владение контрактом

Платон поддерживает общие типы и OpenAPI. Артём и Даниил используют их без переименования. Изменение интерфейса сначала фиксируется в этом документе и схемах, затем синхронно внедряется в потребителях. Разработка должна продолжаться на mock-адаптере, если соседний блок ещё не готов.
