# План интеграции и приёмки

## Первый рабочий отрезок

| Время, ориентировочно | Платон | Артём | Даниил |
| --- | --- | --- | --- |
| Первые 20 минут | Проверить контракты и env, уточнить структуру примера сабмита | Скачать данные локально, проверить структуру базы | Прочитать API и fixture, подготовить Vue |
| До 2 часов | API чата на явно обозначенном mock-retriever, подключение LLM | Загрузчик, нарезка и BM25 | Чат и карточка на mock API |
| К 3–4 часу | История сессии и подключаемое ядро | `build_retriever` и поиск по полной базе | Переключение mock/real, состояния ошибок |
| Первая сборка | Подключить retriever Артёма | Проверить источники на запросах | Подключить API Платона |

Не ждать завершения всех соседних задач: использовать опубликованные интерфейсы. Mock должен быть явно обозначен; перед общей проверкой его отключают.

## Порядок объединения

Платон принимает изменения через PR в `main`: сначала RAG-модули, затем backend, затем frontend. Если фактические зависимости позволяют, порядок можно изменить; контракт остаётся общим. При конфликте выбирать совместимую реализацию, а не автоматически «всю нашу» или «всю чужую» версию.

После слияния каждый обновляет свою ветку из `origin/main` обычным merge. Общие зависимости и Compose правит Платон после получения списка от участников. Даниил закрепляет frontend-зависимости lock-файлом.

## Проверки до полного MVP

- [ ] Из чата отправлен вопрос; ответ получен по реальному поиску и реальной LLM.
- [ ] В отладке видны использованные источники и отдельные времена поиска/генерации/полного ответа.
- [ ] Следующая реплика учитывает предыдущие параметры, местоимения и текущую тему.
- [ ] Исправление клиентом параметров заменяет устаревшие сведения.
- [ ] Отказ оставить телефон позволяет продолжить консультацию.
- [ ] Отсутствие фактов в базе приводит к ясному ограничению, а не выдуманному ответу.
- [ ] «Новый диалог» и закрытие чата создают чистый контекст; обе прошлые сессии остаются в архиве.
- [ ] Архив содержит разговор без заявки и разговор с заявкой.
- [ ] Только согласие и валидные вымышленные контакты создают заявку; двойная отправка не создаёт дубликат.
- [ ] Заявка содержит проверяемое резюме без выдуманных параметров.
- [ ] Ошибка прокси или тайм-аут показываются понятно и не уничтожают историю.
- [ ] Два параллельных клиента не получают данные соседней сессии.

## Проверки сдачи

- [ ] Прочитан актуальный регламент; обязательные модули лежат в корне ZIP.
- [ ] `solution.py` проходит локальные demo-вопросы и не смешивает ID.
- [ ] `submission.csv` содержит ровно `id,answer`, все исходные ID без повторов, непустые ответы до 10 000 символов.
- [ ] Замерен полный прогон, включая индексирование; он укладывается в 20 минут.
- [ ] Проведён запуск из чистого клона с зависимостями, без скрытых локальных файлов.
- [ ] Итоговый Compose запускает API и UI одной командой и сохраняет SQLite между перезапусками.
- [ ] README описывает реальные команды, порты, сервис/модель, настройки, известные ограничения.
- [ ] Подготовлена PDF-презентация; на первом слайде ссылка на репозиторий и порядок проверки.
- [ ] В Git и ZIP нет секретов и исходных закрытых материалов.

## Измерения

Артём ведёт локальный отчёт по качеству retrieval и случаям потери ограничений. Платон — отчёт по ответам, ошибкам и времени прогона. Даниил — ручную приёмку UI и демонстрационный сценарий. Для скорости фиксировать медиану и p95 на одном и том же наборе, отдельно холодный запуск. Целевой SLA определить после первого измерения, не обещать непроверенную задержку.

В публичные отчёты не копировать исходные вопросы, golden-ответы и фрагменты закрытой базы. Использовать агрегаты и собственные синтетические примеры.
